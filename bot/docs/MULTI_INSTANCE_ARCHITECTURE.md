# Multi-Instance Architecture

## Overview

The system runs an API server that manages multiple isolated bot worker processes.

Flow:

`API request -> BotInstanceManager -> subprocess(main_instance.py) -> trading modules -> exchange`

## Core components

- API server: `src/api/server.py`
- Instance manager: `src/bot_instance_manager.py`
- Worker runtime: `src/main_instance.py`
- Trading logic: `src/trading/*`

## Isolation model

Each instance has isolated state files under `bot_states/`:

- `config_<instance_id>.yaml`
- `bot_agents_<instance_id>.json`
- `cointegrated_pairs_<instance_id>.json`

Global instance index:

- `bot_states/instances.json`

## Lifecycle model

Nominal statuses:

- `STOPPED`
- `STARTING`
- `RUNNING`
- `STOPPING`
- `ERROR`

Lifecycle entrypoints are exposed through API calls that delegate to `BotInstanceManager` methods.

## Process model

- Worker runs as separate OS process
- Manager tracks PID and updates process/resource metadata
- Cleanup task marks dead workers as `ERROR`

## Configuration model

- Environment variables are loaded at startup
- Instance-specific YAML is generated by manager
- Runtime also relies on constants/config loaders in `config/` and `src/constants.py`

## Persistence model

Current architecture is hybrid:

1. **File state** for per-instance runtime tracking
2. **Database state** for broader API/domain persistence (models/repositories)

This split is intentional but requires reconciliation checks during restart/recovery.

## Known constraints

- Some runtime errors terminate worker process to fail closed
- Backtest progress WebSocket updates are not yet implemented
- Some auth/backtest repository paths are placeholders (see `docs/FEATURE_STATUS.md`)
